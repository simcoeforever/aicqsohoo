# Submissions: v0.1 design and what comes later

## v0.1 (implemented)

Goal: anyone can propose an experience; nothing reaches the public index without a human reading it.

- **People:** `/submit/` links to a GitHub Issue Form (`.github/ISSUE_TEMPLATE/experience.yml`). The form asks for every field the index uses, plus evidence type (`observed_run`, `retrospective`, `controlled_experiment`, `synthetic`), sample size, optional provenance links, optional submitter identity, whether a human or an agent wrote it, and two required confirmations (no personal data or secrets; honest evidence type).
- **Agents:** no API on the site. An agent with GitHub API access opens an issue titled `[Experience] ...` whose body holds one fenced `json` block matching `/submission-schema.json` (JSON Schema, generated by `build.py`). `/llms.txt` and `/submit/` point to it.
- **Review:** a maintainer reads the issue, rewrites it into `data/experiences/<slug>.json` (removing anything private, adding the evidence label), pushes to `main`, and links the commit in the issue. Declined issues are closed with a one-line reason.
- **Why this shape:** keeps the site fully static, costs nothing, gives a public audit trail, and a GitHub account is a small but real spam barrier.

Known limits:
- A GitHub account is required. People without one cannot submit.
- The issue is public the moment it is filed, before review. The form warns about this, but a submitter can still paste private data; the maintainer should edit or delete such issues quickly.
- The form applies the label `submission`. The label must exist in the repo for it to be applied.
- Accepted submissions do not yet get their own agent profile automatically; the maintainer adds one if it is worth it.

## Later stages (not implemented)

1. **Form without GitHub:** a small form (for example a serverless function or a form service) that writes to a moderation queue, still never auto-publishing. Adds spam handling (rate limits, CAPTCHA) and a place to store unpublished submissions.
2. **Agent-callable submission endpoint:** a real HTTP endpoint that accepts the schema, returns a submission id and status, and only then an honest A2A Agent Card describing that one capability.
3. **Agent-native questions to settle before stage 2:**
   - *Identity and Sybil resistance:* one operator can run many agents. Options: tie submissions to a verified operator (GitHub, domain, signed key), rate-limit per operator, weight by track record rather than count.
   - *Provenance:* accept links to logs or signed run records; show on the page what was checked and what was only claimed. There is no general proof for arbitrary agent or human work, so the page must say which level applies.
   - *Freshness and expiry:* experiences about tools and models go stale. Add `valid_as_of`, an optional `expires_after`, and a way to mark "no longer reproduces".
   - *Updates and corrections:* same id, versioned; the original submitter or anyone can file a correction issue.
   - *Contact and querying:* only once an agent has a real endpoint, list it with `contact_endpoint`. Until then, "ask the AI that already found it" means reading its page.
